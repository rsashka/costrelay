# Правила и требования к проекту

Файл для агентной разработки: обязательные правила CostRelay. Пользовательская
документация — только [README.md](README.md).

## Документация

1. Вся документация живёт в одном файле — `README.md`. Отдельных `.md` с
   описанием, инструкциями и HOWTO нет; новый файл документации не создаётся,
   содержимое дополняет README.
2. README содержит минимально достаточное описание проекта и минимальную
   инструкцию по настройке и запуску. Подробности поведения в README не
   дублируются.
3. Параметры конфигурации и их допустимые значения описываются **только** в
   комментариях шаблона `--init-config` (`src/config/DefaultConfig.h`). Другой
   документации настроек не существует.
4. `.scratch/` — рабочие заметки, логи и проверочные утилиты. Это не
   документация: в репозиторий не попадает (каталог в `.gitignore`).

## Архитектурные требования

1. **Однократность.** Величина вычисляется одним способом, хранится в одном поле
   и читается одним путём. Копия расчёта, второе поле для того же значения и
   пересчёт в месте отображения запрещены: вызывается существующий источник. Что
   видно в панели, API и логах, считает тот же код, что и рабочий путь. Профиль
   токенов один — наблюдаемая средняя модели; отдельного профиля под конкретный
   запрос нет.
2. **Единственная очередь.** Порядок провайдеров вычисляется один раз при
   перестроении очереди и публикуется снимком (`ProviderQueueSnapshot`); панель,
   API, explain и живой запрос читают этот снимок, а не считают маршрут каждый
   по-своему. Живой запрос маршрут не пересчитывает. Порядок задаёт только
   `weight RUB/M` — `computeTokenCost` по текущим ценам каталога и наблюдаемому
   профилю токенов модели с поправочными весами `routing.output_weight` и
   `routing.cache_weight` плюс цена наблюдаемой задержки провайдера по
   `routing.wait_price_rub_per_sec`. Цены — только текущий прайс: статистика
   задаёт пропорции токенов (вход/выход/кеш) и задержку, но никогда не подменяет
   цену.
   Фильтры (чёрный и белый списки, контекст, статус) исключают кандидатов и
   порядок не меняют.
3. **Расписание.** Очередь перестраивается сразу после обновления прайса и
   фоново: случайный тик `routing.queue_min_sec`…`queue_max_sec` (по умолчанию
   600–900 с) — если изменились цены; изменение статистики запросов — не чаще,
   чем раз в `routing.queue_stats_sec`. Изменение политики из панели (чёрный
   список, импорт CSV, настройки маршрутизации) перестраивает очередь сразу.
4. **Только текущие факты.** Требования, комментарии и тексты интерфейса
   описывают текущее поведение: без истории версий, прежних правил, причин
   изменений и кода для обратной совместимости. Схема конфигурации и схема БД
   живут одной версией: переименование ключа — это замена, а не псевдоним;
   добавление колонки — идемпотентное (`StatsDb::ensureColumn`), без пересоздания
   базы.
5. **Минимум комментариев.** Комментарий нужен, только если он сообщает
   неочевидное: инвариант, единицу измерения, внешнее ограничение. Запрещены
   пересказ кода, перечисление вызывающих функций, очевидные примеры, вода.
   Неочевидное лучше выразить именем, типом или отдельной функцией.
6. **Профиль из статистики.** Очередь и цены считаются на реальных средних
   входных, выходных и кешированных токенах модели — одном профиле для панели,
   API и живых запросов. Источник профиля один: `routing.profile_sample_size`
   (0 — средняя по журналу запросов, N — последние N успешных запросов модели из
   кольца; пока после перезапуска окно не набрано, берётся средняя по журналу), и
   предпросмотр в панели считает тем же кодом с ещё не сохранённым значением. Оценка «1000/500» применяется только там, где
   наблюдений ещё нет, и в интерфейсе помечается как оценка. Наблюдение профиля —
   успешный запрос с отчётом о токенах (`tokens_in > 0`), наблюдение задержки —
   успешный запрос с измеренной задержкой; запрос без отчёта не разбавляет
   средние. Сброс кеша меняет только попадания: запросы до сброса (модели,
   сессии или провайдера) не входят в среднюю долю кеша, но вход/выход остаются
   в профиле. Окно и журнал считают это одним правилом — перезапуск профиль не
   меняет.

## Инварианты и антипаттерны

1. **Инвариант прежде кода.** У любого преобразования общего состояния (порядка,
   набора, полей, файла) есть сформулированный инвариант: что сохраняется, что
   меняется и насколько. Код выражает ровно это. Нет подходящего примитива —
   вводится именованная операция с этим инвариантом; выбирать стандартный
   алгоритм «похожего назначения» запрещено, его семантика может быть шире
   требуемой.
2. **Минимальность изменения.** Операция затрагивает только необходимое. Данные,
   которых изменение не касается, сохраняют значение и взаимный порядок.
   Преобразование, способное затронуть больше, — дефект, а не удобство.
3. **Контракт вместо догадки.** Перед использованием чужой функции или алгоритма
   выписывается её контракт: что читает, что пишет, что и в каком порядке
   сохраняет, как ведёт себя на краях. Контракт шире требуемого — обернуть и
   сузить, а не рассчитывать, что «на наших данных сработает».
4. **Один владелец преобразования.** Общую структуру преобразует ровно одно
   место, остальные читают. Локальная пересборка, повторная сортировка,
   фильтрация и склейка у потребителя — второй источник истины и запрещены.
   Расхождение двух представлений одного значения или порядка — дефект
   архитектуры, а не отображения.
5. **Явные побочные эффекты.** Функция, которая по назначению выбирает,
   проверяет или читает, не переписывает общее состояние; изменение общего
   состояния — только у явно названной операции.
6. **Свойство, а не пример.** Тест проверяет инвариант на краевых конфигурациях
   (пусто, один элемент, дубликаты, равные значения, элемент в начале, середине и
   конце, предельные величины), а не один удачный пример. Тест, проходящий на
   ошибочной реализации, ничего не проверяет.
7. **Регрессия — первой.** Ошибка сначала воспроизводится падающим тестом, затем
   правится код. Исправление без теста, падающего на прежнем коде, не принимается.
8. **Правило — на уровне класса ошибок.** После инцидента формулируется класс
   ошибки и правило против него, применимое к другим модулям, а не пересказ
   конкретного места, функции или значения. Нарушение инварианта, найденное в
   одном месте, проверяется тем же инвариантом в однотипных.
9. **Запрещённые антипаттерны:**
   - алгоритм с более широкой семантикой (пересортировка, сдвиг, разворот,
     перемешивание) там, где требуется затронуть один элемент;
   - изменение общего состояния как побочный эффект функции-выбора или чтения;
   - пересчёт, пересортировка и переупаковка в панели, API и логах;
   - неявная зависимость от текущего расположения или состояния данных без
     проверки инварианта;
   - копия расчёта, правила, порога или константы вместо вызова существующего
     источника;
   - неявные единицы измерения, диапазоны, направления сортировки и знаки;
   - обход общего пути «временной» или частной логикой;
   - молчаливое подавление ошибки вместо её видимой фиксации (отказ, лог, код).

## Текущие требования к маршрутизации

1. **Один провайдер в запросе.** `provider.order` собирает
   `routing.provider_order_size` тегов (по умолчанию 1) с
   `allow_fallbacks: false`, первым — провайдер текущей попытки. Смена
   провайдера на стороне внешнего обработчика запрещена; отказ виден как ошибка.
2. **Гистерезис лидера.** Верх очереди — лидер модели. Он удерживается, пока
   допущен; challenger становится лидером только при выигрыше ≥
   `routing.leader.margin_percent`, выигрыше `confirm_builds` перестроений подряд
   и простое прежнего лидера ≥ `min_dwell_sec`.
   Исключение лидера (чёрный список, пропавшая цена, контекст, статус оффера)
   меняет его немедленно. Состояние лидера хранится в
   `routing.leader.state_file` (по умолчанию `<data_dir>/routing-leader.json`) и
   обязано переживать перезапуск.
3. **Привязка сессии.** Кеш провайдера принадлежит беседе, поэтому пара
   (сессия, модель) закрепляется за провайдером; таблица ограничена
   `routing.session_pin_max` с вытеснением LRU. Привязка — наложение на снимок:
   выбирает первую позицию среди допущенных кандидатов, цены не пересчитывает,
   снимок не меняет. Привязка держится, только пока сброс кеша дороже выигрыша:
   как только лучший оффер дешевле провайдера сессии на
   `routing.leader.margin_percent`, она снимается сразу, без ожидания
   подтверждений лидера. Ниже порога привязка живёт `routing.session_pin_sec`
   бездействия (0 — выключено). Перепривязка всегда логируется, снятие по порогу
   имеет причину `session_cost_rebind`.
4. **Обязательная запись инцидента.** Смена провайдера у серии с потерей кеша
   (`cache_read` был > 0 и стал 0) и ростом стоимости ≥
   `routing.cache_loss_spike.ratio` в пределах `routing.cache_loss_spike.window_sec`
   пишется в журнал обязательно: `error_code = provider_switch_cache_loss`,
   важность 1, JSON `event_detail` (`cause`, `from`, `to`, `ratio`,
   `prev_cost_nano`, `cost_nano`, `prev_cache_read`, `tokens_in`, `gap_sec`),
   `LOG_WARN` и счётчик `costrelay_route_cache_loss_total{model,provider}`.
   Предикат не использует абсолютных цен: предыдущая стоимость должна быть
   просто больше нуля, оценки (`cost_estimated`) в предикат не входят.
5. **Пороги — только из конфигурации.** Любая константа алгоритма (отношение,
   окно, маржа, удержание, подтверждение, TTL привязки, предел таблицы) — ключ
   `routing.*` с валидацией в `AppConfig::validate` и описанием в шаблоне.
   Числовых порогов «в коде» быть не должно.
6. **Диагностика смены.** Вынужденная смена провайдера без всплеска получает
   `error_code = provider_affinity_rebind` (важность 1) и запись в лог; явный код
   вызывающего (например, `cache_miss_blacklist`) не перезаписывается, но событие
   всё равно фиксируется в `event_detail` и счётчике.
7. **Повтор у провайдера.** Отклоняемая ошибка (сеть, таймаут, 429, 5xx, пустой
   ответ) даёт `routing.retry.attempts` повторов у того же провайдера с паузой
   `routing.retry.backoff_ms`. Пока ожидание выгодно (цена потерянного времени
   ниже разницы стоимости следующего оффера, не дольше
   `routing.failover_wait_max_sec`), попытки идут к тому же провайдеру; решение
   о смене принимается по цене, а не по счётчику попыток. Бюджет fallback считает
   провайдеров, а не попытки.
   Тело запроса живёт в памяти процесса и на диск не пишется. Ответ без вывода
   (нет текста, reasoning и вызова инструмента) считается отказом провайдера:
   поток не отдаётся клиенту до первого содержательного фрагмента, поэтому его
   можно повторить. Каждая неудачная попытка пишется предупреждением в лог и в
   `event_detail` запроса (`retries`: провайдер, статус, текст ошибки, номер
   попытки); начатый поток не повторяется.
8. **Неработающий провайдер.** Отказы копятся в серию по запросам (ожидание
   восстановления внутри запроса серию не накручивает): провайдер уходит из
   маршрута после `routing.health_fail_threshold` отказов подряд или после
   `routing.health_down_after_sec` секунд непрерывных отказов (0 — правило
   выключено). Живой запрос сразу идёт следующему по очереди, привязка сессии
   снимается с причиной `provider_down`; оффер остаётся в снимке с исключением
   `provider_down`. Переход в «не работает» — `LOG_ERROR`, отказ каждой попытки
   — `LOG_WARN`; без провайдера запрос возвращает 503, а отказ — `LOG_ERROR`.
   Провайдер вне маршрута проверяется минимальным запросом раз в
   `routing.health_probe_interval_sec` и возвращается после
   `routing.health_recover_successes` успешных проверок подряд (`LOG_INFO`).
   Пока провайдер не работает, главная страница показывает сообщение
   «Провайдер не работает» с причиной и временем.

## Конфигурация и секреты

1. Единая схема без версий. Верхнеуровневые блоки: `proxy`, `panel`, `portal`,
   `models`/`default_model`/`aliases`, `providers.external`/`providers.local`,
   `consumers` и необязательные `analytics`, `capture`, `blacklist`, `whitelist`,
   `stats`, `pricing`, `routing`.
2. Новый параметр — это всегда: поле в `Config.h`, разбор в `Config.cpp`,
   проверка в `AppConfig::validate`, строка в шаблоне `DefaultConfig.h`, при
   необходимости — снимок в панели/API. Ключ без валидации и описания не
   добавляется.
3. Секреты — только `file:/путь` или `env:ИМЯ`, литералов в YAML нет; в конфиге
   хранятся хеши паролей и токенов, не сами значения. Секреты не попадают в git,
   логи и сообщения об ошибках.
4. Относительные пути считаются от каталога файла конфигурации
   (`anchorPath`), а не от рабочего каталога процесса.
5. `routing.leader.state_file` пустой означает `<data_dir>/routing-leader.json`;
   каталог создаётся при записи, запись атомарная (`.tmp` + `rename`).
6. Изменение файла конфигурации из панели сохраняет комментарии остальных строк
   (`saveRoutingBool`/`saveRoutingNumber`/`saveProviderBlockList`).

## Безопасность

1. Панель ограничивается `panel.allowed_networks`; в production задайте CIDR.
2. TLS — двухуровневый: серверный сертификат выпущен локальным УЦ
   (`scripts/gen_local_ca.sh`). Приватный ключ УЦ `state/pki/ca.key` с сервера не
   уходит.
3. Портал не передаёт cookie панели локальному сервису, переписывает `Location` и
   `Set-Cookie`, проверяет роли; локальные приложения считаются доверенными и
   обязаны поддерживать base path.
4. Тела запросов и ответов не сохраняются, если не включён `capture`.

## Код и стиль

1. C++20, сборка без предупреждений `-Wall -Wextra -Wpedantic`.
2. Значения времени, денег и токенов передаются в существующих типах
   (`NanoRub`, `CostMix`, `RequestRecord`), дублирующих структур не вводится.
3. Важность записи журнала считается только в `issueSeverity`, текст кода — в
   `issueText` (новый код обязан иметь текст).
4. Предикат инцидента — только в `Stats::classifyIncident`; причина смены
   провайдера — только из `ProxyService::applyRouteSwitch`.
5. Порядок кандидатов и привязок — только в `ProviderQueue::planFromEntry`;
   `Router::quotes` сортирует кандидатов, `providerPayload` собирает объект
   `provider` из плана.
6. Магические числа в логике отсутствуют: либо ключ конфигурации, либо именованная
   константа рядом с местом использования.

## Данные и статистика

1. Журнал запросов — SQLite (`stats.sqlite_path`, по умолчанию
   `<data_dir>/stats.db`). Отказ хранилища не фатален: прокси работает и сообщает
   ошибку.
2. Удаление записей из журнала уменьшает суточные агрегаты; счётчики Prometheus и
   агрегаты текущего процесса не пересчитываются. Это осознанное поведение.
   Итоги «за всё время» читаются из суточных агрегатов: они живут
   `stats.aggregates_retention_days` и не уменьшаются чисткой журнала по
   `stats.requests_retention_days`. Повторная запись того же `request_id`
   вычитает прежний вклад из агрегатов, сутки не удваиваются. Суточные агрегаты
   хранят и число ошибок (`severity ≥ 2`), и предупреждений (`severity = 1`);
   повтор после отказа считается предупреждением.
3. Сброс статистики кеша (`resetCache`) меняет наблюдаемую долю кеша и
   учитывается очередью при следующем перестроении.
4. Ряд серии (session, model) и привязки живут в памяти процесса; после
   перезапуска ряд начинается заново, привязка восстанавливается текущим лидером.
5. Стоимость запроса — только факт по `usage` провайдера; запрос без отчёта
   стоимости не даёт. Его оценка по наблюдаемому профилю модели хранится в
   `cost_estimated_nano`, показывается отдельной строкой и не входит в
   `cost_nano`, суточные агрегаты, бюджеты и счётчики стоимости.
   Главная показывает ошибки и предупреждения текущих суток из суточных
   агрегатов; ненулевое значение ведёт на страницу «Логи» с фильтром по этому дню
   (UTC) и важности. Сама страница «Логи»: провайдеры выше, журнал и его фильтры
   (день, сессия, модель, провайдер, важность) — внизу. Сравнение стоимости
   суток с прошлыми показывается только как полные прошлые сутки, без процента
   к неполным текущим.

## Тесты и проверка

1. Каждое изменение маршрутизации, статистики и конфигурации сопровождается
   тестами: `tests/test_routing.cpp`, `test_stats.cpp`, `test_statsdb.cpp`,
   `test_config.cpp`, `test_proxy.cpp`; сквозные сценарии — `test_app_integration.cpp`
   с `scripts/mock_routerai.py`.

1. Не перезапускать `costrelayd`, `dsh-web` и `strata` без явной просьбы: это
   прерывает живые запросы и сессии.
2. Не менять и не удалять `state/` (боевая статистика, цены, лидер, привязки) и
   `state-local/`, кроме осознанной проверки на копии.

   без предупреждения о последствиях для клиентов.

   TLS-материалы: они перечислены в `.gitignore` и должны там оставаться.
